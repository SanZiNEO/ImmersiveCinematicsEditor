# 输入、焦点与按键路由

> 状态：未实现
> 范围：入口键、ESC 与飞控键语义、鼠标与文本焦点、玩家输入屏蔽、面板手势作用域、图节点悬停提示
> 关联：14-02 宿主界面、14-04 端点、14-06 飞控

## 一、摘要

游戏内编辑器抢的是玩家正在用的键盘和鼠标。一个键要能开能关还能改绑，一个 ESC 要按上下文决定是失焦、退出飞控还是关闭界面，文本输入框拿到焦点时不能被全局快捷键抢走字符，界面开着时玩家不该还能用 WASD 走位。本文定这套输入规则——谁先消费、什么情况下让位、关闭时怎么还原。飞控算法与画面渲染不在本文。

## 二、为什么做

### 2.1 问题

入口键最容易分叉。主模组原本用一个旧键打开 WebUI，如果游戏内界面为了自己方便再加一个键，用户就要记两个键，而且两个键可能打开两个界面。更隐蔽的问题是硬编码：界面里直接判断某个物理键，用户改绑之后旧键仍然生效，改绑功能形同虚设。

ESC 的歧义同样会伤到用户。编辑器里有文本输入框、有飞控、有面板焦点，同一个 ESC 在三种状态下做三件不同的事。如果规则不统一，用户在输入框里按 ESC 会直接关掉整个编辑器，丢掉没保存的改动。

玩家输入是最容易漏的一条。游戏内界面通常不暂停游戏，界面开着的时候玩家仍然能走能跳，鼠标点击世界还能转视角。用户会看到自己在编辑时角色乱跑，甚至误触方块。这类问题不会报错，只会让人觉得"这个编辑器不牢"。

悬停提示是这一轮唯一的功能性输入需求：把鼠标放到图里的脚本上，要能看到这个脚本的全部触发条件，包括它依赖哪些前置脚本。只显示第一条触发器，或者只显示"依赖 3 个脚本"这种计数，等于没给信息。

### 2.2 目标

- 一个可改绑的入口键负责开关当前活动载体；改绑后旧键失效，重启后保留。
- ESC 与飞控键的语义唯一：先处理飞控，再处理焦点，最后才关闭界面。
- 文本焦点时字符键归输入框，全局快捷键不抢。
- 界面打开时玩家移动键不驱动角色；关闭后立刻恢复，不残留。
- 面板手势各管各的：拖动节点不改片段，主轴与局部轴的滚轮不互相干扰。
- 图节点悬停显示该脚本全部触发条件与全部前置关系。

### 2.3 非目标

- 不实现飞控逻辑本身，只定义它与输入的接缝。
- 不做按键自定义界面：改绑走原版按键设置。
- 不为每个面板各定一套快捷键。
- 不承诺输入法完整支持；宿主能力不足时记录限制并给出替代输入方式。

## 三、方案

用户视角上，游戏内编辑器与桌面编辑器的手感应该一致：能打字、能拖动、能滚动，关闭后回到游戏。

入口只有一个键，默认 `F6`，绑定名 `EDITOR_OPEN`，可在原版按键设置里改。界面内部不认物理键，只认这个绑定是否被按下。同一个键再次按下就是关闭；如果此时正在飞控，先取消飞控再关闭——不把"关闭界面"当成"记录飞行结果"。旧的 `F9` 不再是编辑器打开键，也不保留 `F8` 或任何第二个入口。

ESC 按上下文分层：飞控中先取消飞控；有文本焦点先失焦；两者都没有才关闭界面。这样用户在输入框里按 ESC 只是退出输入，不会丢工作。F7 在飞控中用于带记录退出；不在飞控中它不打开任何东西。

鼠标方面，界面打开时鼠标必须可见可点。飞控期间鼠标交给视角，界面不接收点击；退出飞控后焦点回到原来的面板，不跳到某个随机的旧属性。

面板手势按区域划分职责：主时间轴只管片段级的操作，片段效果控件管属性与节点级的操作，快捷属性只做当前目标的值输入，抽屉与对话框管自己的滚动。指针按下后被当前手势持有到释放或取消，节点拖动不会顺手把片段拖走，两个轴的滚轮各自拥有视口。

悬停提示是图视图的一部分：鼠标进入节点时展示该脚本的全部触发器，每个触发器给出条件摘要、它依赖的前置脚本（脚本标识、名称、所在文件夹）以及悬空或自引用标记。条件树过长时先给摘要并允许展开，不截断到只剩一条。悬停不改变选择、不打开脚本；点击才打开。

## 四、技术细节

### 4.1 核心模型

输入分三层：Screen 层决定"这个按键/点击是否属于编辑器"，路由层决定"交给哪个面板"，面板层决定"这条手势怎么解释"。飞控是一个独占状态：进入后输入不再往下走，退出后回到进入前的焦点位置。

### 4.2 契约

- 入口键只读主模组的键位映射，不在界面里写死物理键。
- 一次按键只被消费一层：先给页面与焦点，页面消费了 Screen 就不再处理。
- 文本焦点期间不拦截字符键；Tab、方向键、回车、ESC 在面板内规则一致。
- 打开界面时吞掉玩家移动输入，不改玩家的持久状态；关闭时还原。
- 飞控激活时输入独占，界面不接收鼠标与移动键；退出后恢复原焦点。
- 关闭时清焦点、清按下与悬停状态、释放光标；不留 grabbed 状态。
- 悬停数据来自图与触发器的读取结果，不由页面脚本产生。

### 4.3 数据形态

输入状态都是临时的：当前焦点元素、按下集合、悬停目标、手势所有者。它们不进入文档序列化，也不跨会话保留。悬停提示的内容按触发器分组，包含触发器标识与类型、条件摘要、`requires` 前置脚本列表、异常标记；数据是只读快照，不在提示里发起写入。

### 4.4 边界

- 界面不修改全局键位表，只在自身生命周期内接管输入。
- 悬停不写文档、不改变选择。
- 提示框不得超出屏幕；靠近边缘时翻转或收拢，缩放滚动时跟随节点。
- 玩家输入屏蔽只作用于界面打开期间，不影响任何持久设置。
- 飞控期间界面不接收点击，避免"边飞边改"造成的半次命令。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 界面再注册一个入口键 | 保留旧键，另加游戏内键 | 双入口、双界面、互斥无人负责 | 入口必须唯一 |
| 界面内硬编码入口键 | 直接判断物理键码 | 改绑失效，用户以为设置坏了 | 必须读键位映射 |
| ESC 一律关闭界面 | 不区分飞控与焦点 | 输入中按 ESC 丢工作，飞控中被强制中断 | 分层处理才符合预期 |
| 打开界面不处理玩家输入 | 只靠鼠标被 UI 拦住 | 角色乱跑、误触方块 | 键盘输入也要屏蔽 |
| 悬停只显示首条触发器 | 提示框只放一条 | 用户看不到其余触发条件与前置 | 必须列全，可折叠不可省略 |
| 用页面脚本绑定悬停 | 依赖页面 JS 做交互 | 当前环境没有脚本引擎，交互不出现 | 宿主侧绑定元素 |

**本方案的缺点**：

- 输入分层多，出问题时很难判断是哪一层吃掉了事件，需要逐层日志。
- 玩家输入屏蔽是"吞掉"而不是"暂停"，某些模组的自定义移动仍可能穿透。
- 悬停提示在触发器很多的脚本上会很长，即使折叠也需要用户主动展开。

### 验收要点

- 默认入口键打开界面；改绑到其它键后旧键无效、新键生效，重启后保留。
- 文本输入框可输入中英文与数字；ESC 第一次失焦、第二次关闭，不双触发。
- 鼠标可见、可点击、可滚动、可拖动面板；关闭后光标恢复。
- 界面打开时玩家移动键不驱动角色；关闭后恢复；玩家持久设置未被改动。
- 飞控中 ESC 取消飞控、再 ESC 关闭；F7 带记录退出；飞控中点击界面无效。
- 图节点悬停列出该脚本全部触发器，每个都带条件摘要与前置脚本信息，悬空与自引用有标记。
- 提示框靠近屏幕边缘时翻转或收拢，不越界；缩放后仍跟随节点。
- 拖动片段效果控件里的节点不会移动片段；两个轴的滚轮互不串。
