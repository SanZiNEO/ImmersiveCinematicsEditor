# AUI 宿主界面与工作台外壳

> 状态：未实现
> 范围：游戏内编辑器的 Screen 宿主、页面骨架、面板挂载点、打开与关闭时机、错误页
> 关联：14-01 附属模组、14-03 帧源、14-07 释放

## 一、摘要

游戏内编辑器需要一个"壳"：一个 Screen，加载 AUI 页面，提供顶栏、中央真实游戏画面、两个属性面板、主时间轴、抽屉和状态栏的位置，并保证游戏继续运行、HUD 保留、鼠标可用。本文定这个壳的职责与时机——什么时候打开、页面里必须有哪些位置、加载失败时用户看到什么。各面板内部做什么不在这里。

## 二、为什么做

### 2.1 问题

把桌面编辑器直接当成游戏内界面来想，第一反应是"把它画到世界里"，于是用世界窗口承载 UI。这条路会立刻出问题：世界窗口参与世界渲染，也参与捕获，编辑器界面会出现在自己的预览画面里，形成套娃，而且退出时很难干净地拆掉。

暂停也是陷阱。游戏内编辑器需要看真实画面在动、需要播放、需要飞控，任何"打开界面就暂停游戏"的默认行为都会让预览静止，用户会以为捕获坏了。反过来，如果给界面加全屏半透明黑底，HUD 被盖住，用户又分不清自己在看画面还是在看遮罩。

还有一类问题发生在关闭时。宿主框架在关闭回调里会先销毁页面文档，再交回子类；如果释放资源的代码写在父类调用之后，那时候页面元素已经不存在，释放动作要么拿不到对象，要么抛异常。这不是偶发，而是必然。

### 2.2 目标

- 按入口键后出现一个完整的工作台外壳：顶栏、中央画面容器、两个属性面板、主时间轴、抽屉、状态栏、错误层都在位。
- 游戏继续 tick 与渲染，HUD 保留，中央画面能显示真实游戏内容。
- 同一时刻只有一个编辑器界面；从另一个载体切过来时先关再开，不叠加。
- 页面缺失、元素缺失、文档创建失败、无帧、端点挂载失败都有可见说明，不白屏、不静默。
- 关闭后回到游戏，再次打开不残留上次状态。

### 2.3 非目标

- 不实现任何面板业务；面板内容由 14-09 逐模块迁移。
- 不在这里挂端点、不订阅帧源、不注册全局输入：这些由后续任务按需接入。
- 不自造释放顺序：统一走 14-07 的释放路径。
- 不提供系统窗口能力（最小化、最大化、独立窗口）。

## 三、方案

用户按一次入口键，看到的是一个铺满窗口的界面，顶部有项目名与保存/校验/播放控制，中间是游戏画面，两侧或下方是两个属性面板，底部是主时间轴与状态栏。鼠标可以点、可以滚、可以拖面板，游戏世界在背后继续运行。

这个壳只负责"位置与骨架"，不负责"内容"。它保证每个面板都有一个明确的挂载位置，并且这些位置是彼此独立的：`clip.effects` 与 `selection.properties` 是两个独立面板，可以同时可见，谁也不是谁的标签页，也不共用旧的对象/关键帧标签；主时间轴只编排片段，不出现对象子行与关键帧节点。

打开是有条件的。没有进世界不打开，宿主总开关关闭不打开，另一个编辑器界面已经在栈里则先关闭再打开。打开动作本身只建立界面与页面，不预先建立端点、不预先订阅画面——这些在页面加载成功之后按需接入，避免"界面没起来但资源已经占住"。

关闭走一条统一路径，并且必须在宿主框架销毁页面之前完成。壳自己不发明释放顺序，它只是把"现在要关了"这件事交给释放路径，由后者决定先停哪一步。重复关闭是常态（用户连按、退世界时框架也会调一次），所以这条路径必须幂等。

页面加载失败不是崩溃。缺页面、缺元素、文档创建失败、无帧、端点挂载失败，各有各的说明，用户能看到原因和"关闭"这条出路，而不是面对一片空白。

## 四、技术细节

### 4.1 核心模型

壳有三个角色：Screen 本身负责生命周期与输入入口；页面文档负责视图与元素；控制器负责把"文档里的元素"和"编辑器状态"接起来。壳不持有业务数据，也不缓存文档对象——它每次需要时向宿主框架要当前文档。

### 4.2 契约

- 打开时校验宿主总开关与模式列表是否包含游戏内模式；不满足则不创建任何东西。
- 打开时若已有编辑器界面存在，先关闭它；两个界面不允许共存。
- 页面加载成功后建立文档与面板绑定；加载失败进入错误页，不继续绑定。
- 关闭与移除两个入口共用同一套释放逻辑；释放必须在宿主框架销毁文档之前执行。
- 释放只处理本界面拥有的东西：本端点的飞控、端点挂载、帧租约、输入状态、文档注册。不关闭捕获中心、不停止 WebUI 服务、不广播飞控退出。
- 尺寸变化只重新应用视口，不重建文档，也不重载页面。

### 4.3 数据形态

页面必须提供完整的一组挂载位置：一个主题与缩放的根作用域、顶栏、项目图入口、中央画面容器、两个属性面板、主时间轴、抽屉宿主、状态栏与错误层。它们是契约而不是建议——缺任何一个都要报错，不允许"找不到就跳过"。判断标准不是元素叫什么，而是每一类内容都有地方放，且放进去之后互不遮挡。主题、布局、偏好不写进页面本地存储，而是走游戏配置目录；页面本身不直接读写文件。

### 4.4 边界

- 不用世界窗口承载编辑器 UI；编辑器 UI 只在 Screen 层，捕获点在 HUD 之后、Screen 之前，所以界面不会进入画面。
- 不在渲染回调里做文件读写、网络请求或重计算。
- 不把页面脚本当成唯一交互入口：当前环境没有脚本引擎，交互由宿主侧绑定元素完成。
- 不与 WebUI 预览屏同时存在。
- 入口键只认主模组的键位映射，不在 Screen 里硬编码按键。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 用世界窗口承载 UI | 把编辑器画在世界渲染层 | 界面进入自己的捕获画面，形成套娃 | 捕获点与 UI 层必须分离 |
| 打开即暂停游戏 | 界面打开时暂停世界 | 预览静止，播放与飞控失效 | 游戏内编辑器要看到真实运行的世界 |
| 加全屏半透明黑底 | 默认背景盖住世界 | HUD 被遮，用户分不清画面与遮罩 | 保留世界与 HUD 才符合"在游戏里编辑" |
| 一个页面塞所有面板 | 用标签页切换面板 | 无法同时看片段效果与属性 | 两个面板职责不同，必须并存 |
| 关闭时各资源自行释放 | 每个控制器自己处理 | 顺序不可控，重复释放 | 统一路径才能保证幂等 |

**本方案的缺点**：

- 页面里的挂载位置是硬约束，任何一次改版都要同步维护，缺一个就报错。
- 游戏内屏幕空间有限，面板一多就拥挤，窄窗口下体验明显不如桌面。
- 错误页能说明问题，但用户在错误页里做不了任何编辑，只能关掉重来。

### 验收要点

- 进世界后按入口键打开界面：顶栏、中央画面容器、两个面板、时间轴、抽屉、状态栏、错误层均存在。
- 游戏不暂停、HUD 保留、背景不被遮住；中央画面在帧源接入后显示真实内容。
- 页面缺失时显示错误页并可关闭；关闭后回到游戏，再次打开正常。
- 从 WebUI 切到游戏内：先关闭前者再打开后者，无两个界面叠加。
- 两个属性面板可同时可见；主时间轴中没有对象行与关键帧节点。
- 宿主总开关关闭时按入口键不创建界面、不建立任何挂载。
