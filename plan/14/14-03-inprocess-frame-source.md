# 进程内 GPU 帧源与纹理租约

> 状态：未实现
> 范围：捕获画面以纹理租约形式交给游戏内界面，含代数、无帧占位、所有权与线程约束
> 关联：14-00 GPU 前置、14-02 宿主界面、14-04 端点

## 一、摘要

游戏内编辑器中央显示的是真实游戏画面。这条画面通路不走 CPU 读回、不做视频编码、不做截图轮询：捕获中心已经把画面渲染进一张固定纹理，编辑器以租约形式借走这张纹理，直接在自己的界面里画。本文定这条通路的边界——谁拥有纹理、租约什么时候失效、没画面时用户看到什么。

## 二、为什么做

### 2.1 问题

桌面端预览的路径是捕获、CPU 读回、编码、走 WebSocket 传给浏览器。搬到游戏内之后这条路径的每一段都变成纯开销：同进程之间不需要序列化，纹理可以直接用，编码只是给网络用的。如果照搬，用户会得到一帧延迟、额外内存带宽、以及一条需要维护的编码链路，而画质不会有任何提升。

另一个问题是无帧。捕获是按需的：没人要帧就不抓。界面刚打开、或分辨率变化重建捕获目标的那几帧里没有可用画面。如果这时仍去画旧纹理，用户看到的是花屏或者冻结的上一帧，而他会以为这是"实时预览"。

### 2.2 目标

- 中央显示真实游戏画面，包含 HUD、lane 合成与调色，不包含编辑器自身的界面。
- 只有游戏内消费者时，捕获不产生 CPU 读回；WebUI 的 CPU 消费者同时存在时两者都正常。
- 捕获规格变化后界面自动跟上，不画过期内容。
- 关闭界面只释放自己的租约，捕获中心与其它消费者不受影响。
- 无帧时显示占位，不崩溃、不用旧帧冒充实时。

### 2.3 非目标

- 不重写捕获中心的捕获、格式协商与 CPU 预览路径。
- 不做视频编码、不做网络传输。
- 不用 CPU 读回作为 GPU 路径的回退。
- 不实现编辑器侧的画面处理（叠加、裁剪、滤镜）。

## 三、方案

用户看到的效果很简单：打开编辑器，中央就是游戏画面，动的东西在动，切窗口大小后画面跟着变。关掉编辑器，WebUI 那边该有的预览还在。

实现上，"借纹理"要能说清三件事。第一，谁拥有它：捕获中心拥有，消费者只持租约，租约结束不等于删纹理。第二，怎么判断还能不能用：捕获目标重建时格式代数加一，旧代数的租约停止绘制，等新帧来了再恢复——界面不会把两个不同规格的纹理混着画。第三，什么时候没有画面：刚打开、刚重建、场景切换的那几帧，显示"等待画面"，而不是显示上一帧。

画面里有什么也是契约：捕获发生在 HUD 之后、编辑器界面之前，所以画面里有 HUD、lane 合成与调色，但没有编辑器自己的顶栏与面板。如果用户看到编辑器界面出现在画面里，说明捕获点被挪了，这是失败而不是小瑕疵。

## 四、技术细节

### 4.1 核心模型

捕获中心维持一条消费者列表，其中一类只关心 GPU 帧。GPU 消费者每帧被问一次"要不要这帧"，要就拿走一份元数据；元数据里没有像素，只有纹理标识、尺寸、代数、帧号、时间与方向信息。编辑器侧的 `EditorFrameSource` 把这层元数据包装成租约（`FrameLease`），交给界面绘制。

### 4.2 契约

- 登记与注销都发生在渲染线程；回调里只记录标识与代数，不做重活。
- 一帧的处理顺序是：先把主画面搬到捕获目标，再通知 GPU 消费者，最后才判断是否有人需要 CPU 帧；没有 CPU 消费者就不分配读回缓冲、不读像素。
- 规格变化重建目标时代数加一；旧代数租约停止绘制并进入等待，新帧到达后恢复。
- 一个界面一个租约；关闭界面只注销自己的租约与纹理注册。
- 租约不删除纹理、不关闭捕获中心；捕获中心的关闭仍只由主模组决定。
- 消费者全部不需要帧时不做捕获，沿用现有按需语义。

### 4.3 数据形态

租约对外暴露的是只读元数据：纹理标识、宽高、代数、帧号、时间戳、是否需要翻转、alpha 语义。方向与 alpha 以实际纹理为准，不在文档里写死某个方向，验收以"画面正立、不整帧透明"为判据。代数之外不提供"猜测有效性"的途径。

### 4.4 边界

- 捕获中心的所有权不转移，消费者不碰纹理生命周期。
- 编辑器不复制第二张纹理，也不把整帧搬到 CPU 再上传。
- 纹理注册与更新都在渲染线程；页面层只持元数据与句柄，不直接持有 GL 资源。
- 关闭顺序是先停绘制、再注销纹理注册、最后释放租约，不反向。
- CPU 消费者路径保持原样；GPU 路径不得把 CPU 读回当作回退方案。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 复用 WebUI 的 CPU 帧 | 读回像素再上传成纹理 | 每帧两次搬运、一帧延迟、需要编码链路 | 同进程内没有任何收益 |
| 定时截图轮询 | 按固定间隔截一张图当预览 | 帧率与游戏不同步，画面撕裂 | 捕获中心本来就是按需渲染 |
| 复制捕获纹理 | 每帧从捕获纹理再拷一份给界面 | 显存翻倍，两套生命周期要同步 | 租约不改所有权，代价最小 |
| 关闭时顺手释放纹理 | 界面关闭即删纹理 | WebUI 与其他消费者直接失效 | 生命周期归捕获中心 |
| 无帧时保留上一帧 | 没新帧就继续画旧的 | 用户以为画面卡住但其实是实时 | 占位比假实时诚实 |

**本方案的缺点**：

- 代数机制要求消费者自己判断有效性，写错的表现是花屏，且小窗口下不容易发现。
- 只有 GPU 消费者的优化路径与 CPU 路径分叉，两条路径都要各自验证，测试面变大。
- 无帧占位在场景切换时会短暂出现，观感上像闪一下。

### 验收要点

- 打开界面后中央显示真实游戏画面，含 HUD、lane 合成与调色，不含编辑器顶栏与面板。
- 只有游戏内消费者时，捕获不分配读回缓冲、不读像素，画面仍持续更新。
- WebUI 的 CPU 消费者与游戏内消费者同时存在时两者都正常。
- 分辨率或规格变化后代数递增，界面更新尺寸并继续显示，不再绘制旧代数内容。
- 关闭界面后租约与纹理注册被注销，捕获中心仍存活，WebUI 预览仍可用。
- 无帧期间显示占位，不崩溃、不显示上一帧冒充实时。
- 换世界后旧租约失效，新世界重新获取，无旧纹理残留。
