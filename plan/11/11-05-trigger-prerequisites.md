# 触发器前置与跨脚本依赖

> 状态：未实现
> 范围：`meta.triggers[].requires` 的两种形态、三种内置前置、目标解析状态、跨脚本依赖视图
> 关联：11-04 条件树、11-11 事实检查器、05 脚本图

## 一、摘要

`requires` 是整条触发器之前的 AND 门：全部满足才允许触发，任一不满足则触发器不求值、也不记录已触发事实。本文定义它怎么存、三种内置前置各是什么语义、目标脚本的解析状态怎么呈现，以及它和条件树内部脚本前置的区别。

## 二、为什么做

### 2.1 问题

`requires` 的元素有两种形态——字符串和对象——但它们不等价：字符串只可能是 `script_played` 的简写。作者若以为字符串能表示"任意前置"，写出来的东西会被解析成另一种语义。更常见的混淆是把 `requires` 与条件树里的脚本前置当成同一件事：前者是外层 AND 门，后者可以放进 `any` 表达"前置满足或位置满足"；前者每次求值都先检查，后者在解锁后持续为真。

跨脚本引用的可靠性也看不见。目标脚本被改名或删除后，`requires` 只是不再成立，作者在编辑器里看不到"这条前置指向了一个不存在的脚本"。同理，目标 id 在项目里不唯一时，运行时无法确定引用谁，而编辑器不会提示。

### 2.2 目标

- 两种存储形态都能读能写，且保存时保持原有形态，不自造第三种。
- 每条前置显示解析状态：已解析、缺失、自引用、重复 id、自定义只读。
- 与条件树内部的前置子条件形态区分清楚，两处不自动互转。
- 依赖关系在行为页的依赖页签与脚本图里说法一致。

### 2.3 非目标

- 不查询"某个玩家是否播过某脚本"。
- 不在编辑器里创建缺失的目标脚本。
- 不新增前置类型，也不为自定义前置提供字段编辑器。

## 三、方案

前置列表是数组，元素可以是字符串（只可能是 `script_played` 的简写）或对象（必须有非空字符串类型，其余键是该前置的数据）。三种内置前置都用 `script` 字段指向目标脚本 id：

- `script_played`：目标脚本既有开始事实又有结束事实，任何退出原因都算。它不是"完整看完"。
- `script_started`：目标脚本有开始事实。
- `script_completed`：目标脚本有结束事实，不要求先开始过。它不是"成功播完"。

三者都是"玩家 + 脚本"维度，与播放实例、退出原因无关，且是锁存语义：一旦成立，后续查询持续为真。

列表每行显示类型、目标脚本 id（内置三种）或"自定义前置"、解析状态、能解析时的目标路径，并提供删除与上下移动。顺序只用于阅读，AND 语义与顺序无关，但保存时保留原数组顺序，不重排。

新增流程是先选类型（三种内置之一），再选目标脚本：可以从项目图索引的脚本 id 列表里挑，也可以手输 id；`requires` 认的是脚本的 `meta.id`，不是文件路径，因此不提供文件选择器。默认写对象形态；若作者选择简写，只有 `script_played` 能写成字符串。类型或目标为空时不允许应用。

编辑已有条目时：字符串简写显示为 `script_played` 但保留字符串形态，改目标仍写字符串；对象形态改类型时保留原 `script`；切到自定义类型时 `script` 变成只读旧字段，不静默删除；自定义类型只显示类型与原始数据只读块，不提供目标选择器，也不伪装成脚本前置。

解析状态由项目图索引决定：目标存在且唯一是"已解析"；不存在是"缺失"，允许手写 id 但不自动创建脚本；等于当前脚本是"自引用"，不阻止保存但警告；id 不唯一是"重复 id，无法确定"，不自动挑先扫到的那个。目标脚本未打开也能引用，不要求先打开文档。

依赖页签与脚本图边共用同一套关系：每个内置前置对应一条潜在边，字符串简写按 `script_played` 建边；自定义类型没有脚本 id，不建边；同一目标重复出现时保留多条 `requires`，图上只画一条边但依赖页显示重复；目标缺失画悬空桩而不创建假节点；自引用不画完整边；成环标"环内前置"，提示可能只能由外部启动打破。图数据里的 `requiresFingerprint` 只用于依赖维护的并发检测，不是作者字段，不在行为页显示，保存流程负责重算。

与条件树内部前置的区别要一直保持可见：位置不同（外层 vs `conditions.list` 内）、语义不同（AND 门 vs 可参与 OR 的子条件）、形态不同（允许字符串简写 vs 必须对象）、锁存不同（每次求值先检查 vs 解锁后持续为真）。两处不自动互转；把字符串子项写进组合器 `list` 是 block 级错误。

## 四、技术细节

### 4.1 核心模型

前置是"触发器外层的与门条件集合"。每个条目要么是内置脚本前置（带目标脚本 id），要么是自定义类型（只有类型与原始数据）。解析状态是派生值：由目标 id 在当前项目图索引里的存在性与唯一性算出，不存盘。

### 4.2 契约

- 目标解析依赖项目图索引的脚本 id、路径、名称、有效性与重复标记。
- 依赖页签与脚本图边共用同一套解析结果，不各算一份。
- 保存时保持条目原有形态（字符串仍是字符串，对象仍是对象）。

### 4.3 数据形态

数组元素两种形态混排是合法的。对象形态的类型字段是唯一必填键；内置三种额外要求 `script`；自定义类型其余键原样保留。

### 4.4 边界

- 编辑器不求值前置，不显示某玩家是否满足。
- 不把自定义前置映射成脚本前置，也不猜它的字段含义。
- 不改脚本图的数据契约；依赖页签只是同一份关系的另一种视图。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 统一只写对象形态 | 读入字符串后立刻转对象 | 保存会改写作者原文，diff 噪声大 | 两种形态都是合法格式，编辑器不该擅自规范化 |
| 用文件路径引用脚本 | 目标选择器选文件 | `requires` 认的是脚本 id，路径改名即失效 | 语义在 id 上，不在路径上 |
| 目标缺失时自动建脚本 | 缺失就创建占位脚本 | 制造空脚本，图里多出假节点 | 缺失是作者要修的问题，不是编辑器替他决定的 |
| 依赖信息只放图里 | 行为页不显示解析状态 | 作者改前置时必须切到图页才能发现缺失 | 编辑现场就该看到引用是否成立 |

**本方案的缺点**：

- 两种形态并存，作者需要理解"字符串只能是 played 简写"。
- 重复前置保留不合并，依赖页会显得啰嗦。
- 自定义前置只能只读展示，无法在编辑器里校验它的数据。

### 验收要点

- `requires` 写字符串：显示为 `script_played → 目标`，保存仍是字符串简写。
- 对象形态写 `script_started`：显示开始前置，不被改写成 played。
- 两条不同目标：都显示，AND 语义说明正确。
- 两条相同目标：都保留；图上只一条边；依赖页显示重复。
- 目标缺失：显示缺失，允许保存，导出时由校验器给警告。
- 目标自引用：显示自引用，不画完整边。
- 目标 id 重复：显示"重复 id，无法确定"，不自动选。
- 自定义前置：只读块，没有目标选择器，不建边。
- 目标写成文件路径：显示"应为脚本 id"，不自动解析路径。
- 组合器内加脚本前置：写成类型加 `conditions.script`，不是字符串也不是顶层 `script`。
- 组合器内前置在 `any` 中：说明它是锁存语义，解锁后持续为真。
- 脚本图悬停：全部前置可见，状态与行为页一致，不截断。
