# 回放检查

> 状态：未实现
> 范围：把"写脚本 → 推给游戏 → 看真实结果"做成一条可操作闭环，只用既有消息
> 关联：08-05 镜头检查面板、08-02 叠化与参数过渡、03 文档序列化、01 消息路由

## 一、摘要

把"当前文档 → 本地校验 → 服务端校验 → 序列化 → 推给游戏 → 跳转 → 播放/暂停/停止 → 状态回执 → 看真实画面"接成一条闭环，放在镜头检查面板的回放 tab 里。全程只发已有的八种消息，不新增消息类型，不做本地渲染，不采样像素；真实结果以游戏预览为准。

## 二、为什么做

### 2.1 问题

作者写完脚本后，验证只能靠"手动推一遍、进游戏看一眼"，中间缺少状态反馈：不知道推过去的是哪一版，不知道服务端校验有没有通过、卡在哪一条；推完之后播放头在哪、是否在播、有没有回执，全靠猜；校验失败没有定位入口；文档改过之后已推过去的还是旧版本，界面毫无提示；想确认叠化、参数过渡、共存这些效果，只能反复手动 seek。

### 2.2 目标

- 一条明确的链路：校验 → 推送 → 跳转 → 播放控制，每一步有可见状态。
- 校验失败时能看到问题列表并定位到片段或字段。
- 推送前必须有本地校验和服务端校验都通过，不能把已知非法的脚本送出去。
- 推送与跳转分离：推送保留当前播放头，跳转是显式动作；推送前在播就恢复播放，已暂停就保持暂停。
- 文档改动后状态回到"需重新校验"，不自动重推。
- 只用既有消息，不新增任何 type。

### 2.3 非目标

- 不做本地渲染，面板里不放第二块画布或 WebGL 视口。
- 不采样像素判断效果是否正确。
- 不新增 `camera.push`、`camera.frame`、`path.sample` 之类的消息。
- 不接管编辑器直控相机，不调用设置相机位置或进入飞行的接口。
- 不自动保存文件：脏标记保留，作者自己保存。
- 不改模组 `.java`。

## 三、方案

### 3.1 状态机

面板有一个显式状态，按顺序推进：未连接 → 就绪 → 校验中 → 有效或无效 → 推送中 → 跳转中 → 播放中或已暂停 → 已停止；任意状态可进入错误态。

每个状态下按钮的可用性不同：未连接全禁用；就绪可校验、可推送跳转；校验中禁用；无效可重试校验但推送禁用；有效全部可用；推送中与跳转中禁用重复推送；播放中可暂停、停止、重新推送；已暂停可播放、停止、重新推送；已停止可推送跳转、播放；错误态可重试。

推送本身没有独立回执，所以"推送中"和"跳转中"靠跳转之后到达的播放状态结束。两秒内没收到就显示"未收到状态回执"，保持跳转中，不自动重推、不轮询。断线时清空推送与跳转状态回到未连接，但不清文档。

### 3.2 校验

两道门都必须过：本地校验桥检查字段类型、范围、引用、叠化规则、参数过渡规则；服务端校验检查完整脚本。

本地有错误就不发服务端校验——避免把已知非法的脚本送出去，也避免浪费一次往返。

服务端返回不通过时进入无效态，列出问题；前若干条直接显示，其余折叠；点击问题尝试定位到对应片段或对象路径，定位失败就显示原文。返回通过时进入有效态，记录校验时间与零问题。

传输失败或超时进入错误态，不允许跳过校验直接推送。

校验只读文档：不保存、不推送、不改播放头。

### 3.3 推送与跳转

推送发送完整序列化后的脚本字符串，不是对象；不发送增量、不发送界面状态、不发送 lane 视图。跳转发送主时间轴当前播放头的时间。

推送前不自动保存文件，脏标记保留。推送后不自动播放，由作者点播放。

跳转不改变播放意图：推送前在播的，跳转会让服务端暂停，随后自动恢复播放；推送前已暂停的，跳转后保持暂停，只是画面刷新到新时间。

推送只发一次，不重试、不轮询、不发第二条"刷新"消息。

### 3.4 播放控制

播放、暂停、停止各发一条消息，状态一律以服务端回执为准，不在本地推断。停止后时间保留最后值。

校验未通过时全部播放控制禁用，避免播着上一版脚本却以为看到的是新结果。

文档修订号变化时：已有效的回到就绪，播放中保持播放但提示"脚本已修改，需重新推送"，不自动重推。播放头变化不触发推送，跳转只在显式操作时发。

### 3.5 面板内容

顶部一行状态：连接状态、文档路径、未保存修改数。下面一行状态徽标、校验问题数、上次推送时间。

再下面一行摘要计数：片段数、CAMERA 片段数、叠化数、参数过渡数、共存数。叠化按"A/B 重叠且 B 不透明度两端为 0/1"计数，参数过渡按"过渡类型为 morph"的片段计数，同一交界同时有两者的单独计为共存，三项分开不互相吞并。

再下面一排按钮，然后是播放头与游戏状态的对照：本地主时间轴时间、服务端回报的时间与是否在播，两者不一致时显示差值。

"画面"一行只说明真实画面在游戏预览视口，面板内不放渲染。校验问题列表可滚动。错误条显示原文加重试，不吞错误。

### 3.6 怎么用它确认真实结果

面板只提供跳转和播放，判断靠看游戏画面：

- **叠化**：在重叠区起点、中点、终点各跳一次。应看到两层同时存在、上层逐渐显现、下层始终不透明。
- **参数过渡**：在交界前后各跳一次，看画面是否按通道模式变化。它是一条 lane 的六参数混合，不是两张画面叠化。
- **共存**：在 morph 窗口内跳，只应看到 morph 结果、叠化画面不可见；在窗口外跳，应看到 A/B 两条 lane 仍在合成。不把"两者同时可见"当作通过条件。
- **多 lane**：在重叠区间内跳，看画面是否出现多层合成；lane 表只作结构对照。
- **呼吸**：播一段，看画面是否按脚本抖动。
- **调色**：比较片段内或交界前后的调色变化。
- **玩家移动**：编辑器预览通道不驱动玩家移动，必须在游戏正常播放脚本时验证；面板不声称预览会产生位移。

如果游戏画面与 lane 表不一致，以游戏结果为准；lane 表标注"结构视图"，不自动改写脚本。

## 四、技术细节

### 4.1 核心模型

三个部分：状态机、命令编排、状态归并。

状态机只保存当前状态与最近一次校验/推送的时间戳，不缓存脚本内容。命令编排负责"校验、推送并跳转、播放、暂停、停止"五个动作各自发哪些消息、按什么顺序。状态归并把服务端的播放状态与错误归并进当前状态。

### 4.2 契约

只使用既有消息：`script.validate` 与 `script.validate.result`、`editor.pushScript`、`editor.seek`、`editor.play`、`editor.pause`、`editor.stop`、`playback.state`、`error`。推送的脚本参数是字符串，校验的文档参数是对象——这两个不能混。

状态机的超时只影响界面提示，不影响文档。断线只清推送与跳转中间态，不清文档与播放头。

### 4.3 数据形态

面板状态、上次校验时间、上次推送时间、问题列表都是界面层，不写盘。摘要计数从当前文档只读统计，不写回文档。

### 4.4 边界

不直接操作连接，通过既有消息路由发送；不新增消息类型与脚本字段；不渲染画面、不采样像素；不自动保存、不自动推送、不自动播放；不调用设置相机、进入飞行等编辑器直控接口。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 面板内嵌预览画布 | 本地渲染脚本结果 | 所见即所得，可离线 | 等于在编辑器里重建渲染管线，与"真实画面以游戏为准"直接冲突 |
| 新增一条"推送回执"消息 | 让服务端确认收到 | 状态更准确 | 需要改模组，且现有播放状态已经能表达"跳转后到了哪里" |
| 校验失败也允许推送 | 让作者自己承担 | 链路更短 | 会把非法脚本送进游戏，排查成本转移到更难的地方 |
| 自动保存后再推送 | 保证推的就是文件内容 | 少一步操作 | 保存是作者的显式意图，自动保存会覆盖他不想保存的中间状态 |
| 推送后自动播放 | 少点一次 | 流程更顺 | 作者常常只想看某一帧，自动播放会打乱定位 |
| 用像素比对判断叠化正确 | 截图算差异 | 可自动验证 | 需要截图通道与容差策略，且真实画面受场景影响，误判率高 |

**本方案的缺点**：

- 判断结果仍然靠人眼看游戏画面，面板只能保证"推过去的是这一版"，不能保证"看到的是对的"。
- 推送没有独立回执，只能靠跳转后的状态间接确认；如果服务端跳转后没有广播，界面会停在"未收到回执"。
- 文档一改就回退到"需重新校验"，作者在微调时会频繁重复校验。
- 摘要计数是结构统计，与画面层数不是一一对应（共存时叠化画面可能不可见），容易被误读。
