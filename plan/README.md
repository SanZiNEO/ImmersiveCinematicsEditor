# Z → 0.3.6 编辑器实施总纲

> 状态：未实现（本目录是实施指导，不是本次实现报告）。
> 先完整建设并打磨WebUI，再迁移游戏内AUI，绝不同步开发验收。WebUI正常对接Forge/Fabric；游戏内迁移先Forge，仅Fabric+AUI适配暂缓。见[实施顺序](shared/implementation-order.md)。

## 一、摘要

把现有 Z 轮设计、0.3.6 模组真实脚本模型和已经迁出的编辑器，收敛成 14 个有先后依赖、按类拆分任务的实施轮次。每轮一个数字文件夹，每个类或紧密耦合的小模块一个任务文件；所有任务只服务于生成主模组可以解析、校验、播放的固定格式脚本。

本次只创建计划文档，没有迁移、修复或实现代码。已有 WebUI 组件和运行时能力是可复用基线，不能据此把新编辑器写成“已经完成”。

## 二、为什么做

### 2.1 问题

现有前端仍使用片段级 `keyframes`、`meta.version`、`total_duration` 和旧 HUD 字段；主模组已经使用 `objects`、叶子属性独立时间序列和 `screen_layers`。直接在旧页面继续增加控件，会生成播放器拒绝的脚本。关系图的旧设计是只读展示，也不满足本轮维护文件夹与依赖的要求。

### 2.2 目标

1. **格式正确**：打开、编辑、撤销、保存、重载后，仍是 0.3.6 的同一脚本语义。
2. **能力不漏**：七类内置轨道、meta、异步对象、路径、数学模型、触发、规则、事件、模板、飞控与预览都有唯一 UI 归属和实施任务。
3. **入口清楚**：先进入按文件夹分类的触发关系图；悬停看摘要，打开脚本才进入工作区。取消旧最左侧常驻脚本列表/源码栏。
4. **预览可信**：只显示游戏产生的真实画面；跨进程使用现有原始帧或视频编码流，进程内使用实际支持的游戏画面接口。
5. **轮次闭环**：每轮的功能、边界、错误处理和本轮验收一次完成，不以“后面补”关闭任务。
6. **可派发**：DeepSeek v4.1 Flash 主代理能把完整任务书一次性交给 v4.1 Flash 子代理，不靠会话中途提醒补目标。
7. **应用完整**：主题可切换、面板可缩放移动/停靠、布局与偏好可恢复；不是固定页面加空设置菜单。
8. **元能力整合**：字幕文件导入、批量管理、schema驱动编译为标准脚本是必做；模组不增加字幕工程解析器。
9. **统一编辑器包**：主模组原webui包迁为editor，内部webui/ingame两模式；统一总入口控制整个编辑器开关，详见独立设计文档。
10. **人工使用验收**：不新增自动化测试/单测/CI/测试脚本；每类任务通过实际界面与游戏使用发现问题，按[人工规约](shared/manual-acceptance.md)和[记录模板](shared/manual-checklist.md)操作复验。
11. **新模型工作区**：主时间轴只编排片段；统一片段效果控件同时展示多个处理组及独立属性关键帧；独立快捷属性复用同值命令，不把旧面板和主轴对象行带入新版。详见[工作区合同](shared/effect-controls-workspace.md)。

### 2.3 非目标

不制作通用剪辑软件、不导出成片、不在编辑器复制游戏渲染/播放算法、不改 0.3.6 的字段语义、不修 Fabric AUI、不在本次改代码。新增必要接口只定义实施合同，不能伪称接口已存在。

## 三、方案

### 3.1 阅读与执行顺序

先读 [`shared/product-and-layout.md`](shared/product-and-layout.md)、[`shared/contracts.md`](shared/contracts.md)、[`shared/application-and-integration.md`](shared/application-and-integration.md)、[`shared/agent-dispatch.md`](shared/agent-dispatch.md)，再读当前轮 README 和其全部任务。源码证据规则和实际基线见 [`shared/baseline-and-evidence.md`](shared/baseline-and-evidence.md)。逐源文件去向见 [`shared/source-inventory.md`](shared/source-inventory.md)。美术建议见 [`shared/art-direction.md`](shared/art-direction.md)，附加建议见 [`shared/editor-recommendations.md`](shared/editor-recommendations.md)。应用/字幕补充任务与原轮任务一并必做，不是附录可选项。

验收统一采用人工实际使用；文中正例/反例/黄金脚本是人工场景，不要求自动断言或测试工程。模组正常校验/解析/播放是产品功能，仍需实际使用观察。

## 四、技术细节

### 4.1 证据和权威

实施时先读对应源码，再动手。`MOD:` 表示主模组仓库相对路径；`EDITOR:` 表示本仓库相对路径；Java 包前缀简写规则见基线文档。源码路径、符号和行范围共同定位，行号移动时以符号为准，不能只凭旧计划猜类还存在。计划中的新类均是提案，不是已有实现。

### 4.2 两分支一份主体

plan只维护一份需求主体；先webui分支实现并经13打磨完成，再在1.20.1方向按14迁移AUI，不各造一套字段/模板/字幕语义。共享需求不等于同步实现，也不预设Vue/TS可直接在AUI运行。普通业务任务的游戏内段落只用于14迁移，不能改变前阶段出口。

### 4.3 完成定义

每个任务必须交付真实能力、消费者可见错误路径、必要行为验证和实际证据；只有类壳、空面板、TODO、演示数据或 mock 回执不算完成。一轮全部任务完成并通过本轮出口才进入下一轮。已明确属于后轮的新能力不是本轮遗漏，但本轮暴露的合同必须当轮真实可用；缺主模组接口时本轮阻塞，不得靠 UI 假成功进入后轮。

## 五、为什么不选别的

| 备选 | 问题 | 本计划选择 |
|---|---|---|
| 在旧模型上继续补控件 | 新格式无从正确保存，异步关键帧会丢数据 | 先冻结真实 schema 和文档合同，再换交互 |
| 两分支各做一套编辑器语义 | 模板/异步/引用会漂移 | 共享文档与消息合同，宿主局部适配 |
| 图上直接编辑所有轨道 | 项目入口与片段编辑混淆 | 图只管组织/关系；打开脚本再编辑 |
| 前端模拟预览 | 与游戏渲染、HUD、实体、光影不一致 | 主模组真实画面是唯一预览 |
| 等游戏内Fabric AUI修完才做其他载体 | 错误扩大故障范围 | WebUI→Forge/Fabric完整实施；游戏内先完成Forge+AUI |

代价：WebUI模型切换需迁移全部调用方，关系写入需要受控协议；AUI能力与进程内接口在14迁移时实证，不提前压成WebUI前置。
