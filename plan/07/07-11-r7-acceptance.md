# 07 轮验收

> 状态：未实现
> 范围：07 全部能力的行为验收要点
> 关联：07-01 至 07-10 各任务文档、02 字段目录、03 文档模型、06 双面板归属

## 一、摘要

07 的验收对象是「作者能不能把位置、朝向、路径、几何、时间、数学模型和预览做完，并写出一份模组能直接读的脚本」。通过条件必须落在可观察的结果上：编辑器里的行为、保存出来的 JSON、游戏里的画面。文档写得再细也不算通过。当前状态：未实现。

## 二、为什么做

### 2.1 问题

07 的能力大多是编辑器侧的便利层——组合建帧、圆形生成、本地预览——它们不改变写盘格式，所以很容易出现「界面看起来对了，但写出来的脚本运行时不认」。如果没有一份以可观察结果为准的验收清单，这类问题会拖到真游戏里才暴露。

反过来，验收如果写成逐条操作矩阵，它又会变成过程记录：条目越多越像执行日志，而实际需要确认的往往只是几类结构性事实。

### 2.2 目标

- 每个能力都有一条「怎么看出来它成了」的判据，且判据能指向界面状态、脚本字段或游戏行为之一。
- 覆盖四类硬边界：写盘只有既有格式、模组 `.java` 零改动、面板职责不越界、主时间轴不被侵入。
- 失败项如实记录，不改写成通过。

### 2.3 非目标

- 不验收模组侧行为，不改模组测试。
- 不把「文档里写了」当作通过条件。
- 不为手感类体验（拖动跟手程度、动画观感）设自动判据；这类只做一次人工确认并记录结论。
- 不追求逐条编号矩阵；同一类事实合并成一条要点。

## 三、方案

验收按十组推进：组合编辑、位置组、朝向组、路径集合、几何、圆形生成器、时间映射、数学模型、预览，以及护栏与真游戏冒烟合起来的一组。每组的判据写在「六、实现结果」的验收要点里，一组一段，读完能直接判断「这件事成了没有」。

验收的做法是拿一份夹具脚本走完整条链：先在编辑器里改，再看写出的 JSON，最后推送到游戏里看画面。同一份夹具贯穿全部组，避免每组各造一份导致交叉验证失效。改之前先清掉残留的编辑器进程，否则首个用例会因端口占用立即失败。

判据的粒度刻意做得粗：不写「点第 3 个按钮后第 5 行第 2 列应显示 2.350」，而写「三轴各有一条时间完全相等的独立关键帧，脚本里没有组对象」。前者一改布局就失效，后者描述的是这件事的本质。

无法自动验证的部分单独列出，不混进通过项：手感类体验做一次人工确认并记录；真游戏冒烟需要可用游戏实例，不可用时标记未执行；几何的 fixture 只验证采样数值，不验证画布渲染像素。

## 四、技术细节

### 4.1 核心模型

验收的判据来源只有三类：编辑器界面状态（控件可见性、徽标、计数、警告文案）、脚本 JSON（字段存在性与数值）、游戏行为（相机运动、日志）。任何一条判据必须能落到其中一类；落不到的就是「无法自动验证」，单独记录而不是模糊通过。

### 4.2 契约

写盘格式是验收的最终口径：`clips[].objects[path]` 里的 `AnimObject` 与顶层 `paths[]`，两者都不允许出现 `authoring`、组定义、临时 id、UI 状态。一份通过验收的脚本，应该能被模组原样读取。

模组零改动是硬条件：`git diff -- '*.java'` 有任何输出即视为不通过。同样硬的是 `WebEditorApi` 消息清单无新增——预览、生成、组合都在编辑器侧完成。

### 4.3 数据形态

夹具脚本本身就是 07 写盘格式的样本，包含：组合建帧的三轴独立关键帧、一条精确 `arc` 圆、一组 Bezier 分段圆、一条只覆盖部分 `axes` 的路径、一个 `motion_position` 的 `chain` 模型。这份脚本同时用作编辑器验收的输入和真游戏冒烟的对象。

### 4.4 边界

- 手感类体验不设自动判据，只做一次人工确认。
- 十一种几何的 fixture 只验证采样数值，不验证渲染像素。
- 真游戏冒烟依赖外部环境，可能长期处于未执行状态。
- 失败项保留原始记录，不改写成通过。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 逐条编号的操作矩阵 | 每个动作一行，记录操作/预期/实际 | 可追溯性强 | 条目数量膨胀后变成执行日志，维护成本高于收益；同一类事实可以合并成一条判据 |
| 只跑自动化测试 | 不写人工判据 | 可重复 | 07 的多数能力是界面行为与游戏观感，自动化只能覆盖其中一部分 |
| 以文档描述为准 | 对照任务文档逐项打勾 | 省事 | 文档写对了不等于实现对了，07 的失败模式恰恰是「界面看起来对、写盘不对」 |
| 只在真游戏里验收 | 全部推送到游戏看 | 最接近真实 | 一次往返几十秒，参数级错误无法定位；且部分能力（timing 曲线、模型摘要）在游戏里看不出来 |
| 为手感类项设阈值 | 用帧率/延迟数字判定 | 看起来客观 | 阈值与机器相关，换个环境就失效；且手感本身不是 07 的核心风险 |

**本方案的缺点**：

- 合并后的判据粒度较粗，出问题时定位不如逐条矩阵精确。
- 部分能力（面板交互、草稿恢复）仍需人工操作，无法完全自动化。
- 真游戏冒烟依赖外部环境，可能长期处于未执行状态。
- 手感类项只做一次人工确认，回归时不会被覆盖。

验收要点：

**组合编辑。** 同一时刻建帧后，三轴各有一条时间完全相等的独立关键帧，脚本里没有组对象、`groupId`、`members`；批量改值与删帧各一次撤销可全回退；抓取当前值只补没有帧的叶子；配置里加成员后重启生效且不改内核代码；保存重开后脚本无 `authoring`，默认组恢复、自定义组消失。

**位置组。** 三种空间形态的可见性与禁用符合预期；`t > 0` 改 step 字段而三轴缺帧时被拦住，补齐后一次撤销全回退；`t = 0` 的改动不要求三轴帧；不读取的既有字段保留数据并给出校验提示。

**朝向组。** 三段优先级的生效与禁用符合预期；目标不可解析时回退到切线或手动，角度不被改成 0；两个基准轴可各取不同来源；线基准退化时回退 0 并给警告；`yaw_lock` 替换基准再叠加角度；角度不归一化；`orient` 只在属性面板。

**路径集合。** 新建流程产出完整条目；目标片段缺 id 或位置节点不足时新建禁用；端点下拉只有节点时间；引用完整性五个入口都做到「阻止 + 提供删除路径并继续 / 取消」，删除与帧操作同一次撤销；片段改名同步 `paths[].clip`；重复端点对被拦下，部分重叠显示徽标；面板停在 `document.drawer`，关闭重开恢复草稿与选中。

**几何。** 类型下拉列出 11 种加 `line` 别名，`line` 只写 `type`；每种类型的数量与范围约束在本地拦下并定位字段；切换类型清空旧参数且可撤销；点位二选一写 `x/y/z` 或 `dx/dy/dz`；锚点徽标正确，`FREE` 端点偏差可见；保存重开后 11 种参数原样保留。

**圆形生成器。** `0→90` 生成一条符合标准圆弧逼近的 `bezier`；`0→360` 自动四段、闭合、径向误差在半径千分之一内；精确模式写一条 `arc` 且 `script.validate` 通过；顺时针方向正确；三维平面下形状落在指定平面；两种时间策略分别成立；影响面先列出再让作者决定；重新生成按 diff 替换、旧 id 消失、一次撤销全回退；非法输入本地拦下；圆心按片段表达式空间写分量。

**时间映射。** 默认线性、`s(t)` 为对角线；切关键帧自动生成首末两点；中间点取中点并按 `t` 排序；首末项不可改不可删；递减与非 `[0,1]` 值被拦下并定位字段；相同 `t` 与相同 `s` 合法并分别画竖线与水平线；改 `from/to` 后 timing 点不变；切几何类型 timing 保留。

**数学模型。** 六个通道默认「未设置」、无时钟、效果面板零行；摘要正确；`chain`/`blend` 递归可编辑；深度超过 8 层或节点超过 32 个时应用禁用并显示超限路径；参数越界字段级拦下；未知类型与未知参数只警告不自动改写或删除；值域不匹配只警告；保存重开后模型树与未知字段原样保留。

**预览。** 11 种类型都能画出形状与控制多边形；`FREE` 路径移动端点时形状不变、偏差更新；`START` 路径终点只做绑定；`axes` 部分覆盖时只画覆盖轴，单轴切一维图，三轴标注 2D 投影；未知类型不画曲线并显示字段错误；11 组 fixture 全部通过，超差即失败并指出类型与采样点；100 条路径时只预览选中条目。

**护栏。** 保存重开后 `paths[]`、`objects`、timing、模型原样，无 `authoring` 与 UI 状态；推送与导出输出同一份格式；撤销覆盖生成、组合、路径编辑；`npm run build` 通过；`WebEditorApi` 消息清单无新增；路径、位置、朝向只读 `objects` 与 `paths`；效果面板对 `motion_*` 零命中；模组仓库 `git diff -- '*.java'` 为零。

**真游戏冒烟。** 夹具脚本校验无 block/error；推送成功且相机沿圆周运动；定位到起点、中点、终点位置连续、接缝无跳变；改 timing 后暂停与跳变可见而几何形状不变；组合建帧后三轴同时到达、无运行时组行为；保存重进后脚本与预览一致、无临时 id 残留；模组日志无路径或解析异常。
