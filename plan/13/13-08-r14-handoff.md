# 向 14 交接与冻结

> 状态：未实现
> 范围：13 交给 14 的冻结输入——不可重写的合同、必须替换的 WebUI 专属实现、迁移顺序与交接门禁
> 关联：01～12 各轮合同、13-01 总账、13-02 黄金脚本、13-07 已知限制

## 一、摘要

13 的最后一个交付物不是安装包，而是给 14 的一份冻结输入：哪些合同已经通过 WebUI 验收、14 不得重写；哪些是 WebUI 专属、AUI 必须换实现；哪些是 13 的已知限制、14 要接住；14 先做什么后做什么，什么情况下不许启动。14 是 AUI 迁移，先 Forge 后 Fabric。13 未通过，不启动 14。

## 二、为什么做

### 2.1 问题

迁移轮最常见的浪费是从头再想一遍。AUI 的界面要在游戏里画，于是很自然地从"游戏内界面该长什么样"重新设计面板、重新定义字段归属、重新发明选择模型，结果同一个能力有了两套语义：WebUI 里改一个值是一次撤销，AUI 里是三次；WebUI 里转场是交界操作，AUI 里变成了片段字段。等到两条路径都上线，脚本开始不兼容，才发现问题不在宿主而在语义。

另一种浪费方向相反：把 WebUI 的实现整段照搬。把 WebSocket 端点搬进游戏进程，于是游戏自己连自己；把固定 1080p60 的预览配置搬过去，于是游戏内窗口被迫按这个规格出帧；把浏览器的输入模型搬过去，于是输入法焦点逻辑在游戏里彻底失效。

### 2.2 目标

- 明确哪些层是冻结的：字段、文档模型、选择与命令、面板职责与标识、模板字幕转场飞控语义。
- 明确哪些层必须替换：传输端点、画面源、输入模型、窗口与外壳。
- 给出可执行的迁移顺序：先最小闭环，再面板迁移，最后加载器对等。
- 给出交接门禁：13 的哪些结论成立才允许启动 14。
- 划清责任边界：14 发现的问题先判断是宿主迁移问题还是原轮合同问题。

### 2.3 非目标

- 不在 13 里提前实现 AUI 的任何部分。
- 不允许 14 重写字段目录、文档模型、选择与撤销。
- 不允许 14 新建第二套主时间轴、属性面板、效果面板。
- 不允许把 AUI 做成"游戏内嵌一个 WebView"来绕过宿主迁移。

## 三、方案

**冻结原则**——14 迁移的是宿主与呈现方式，不是脚本语义与作者工作流。字段目录、脚本文档、选择与命令与撤销、面板职责与标识、模板字幕转场飞控语义，全部不换；传输端点、画面源、输入模型、窗口外壳、发布版本格式中的加载器段，可以换。

判断标准可以压缩成一句：**作者看到的东西和改出来的脚本不变，只有它出现在哪儿、怎么被点到会变**。

**必须接住的 WebUI 专属实现**——WebSocket 会话换成进程内端点，不在游戏里开 WebSocket 连自己；服务端的端口、token 与 Origin 换成进程内会话注册，不再要求 token；捕获加编码的预览链路换成进程内 GPU 帧源与纹理租约，不再走网络帧头与 H.264；固定的预览规格换成帧源自己的尺寸与刷新策略，不假设固定规格；Electron 窗口、菜单、文件对话框换成游戏内界面与文件选择，不启动 Electron；浏览器的输入法与焦点模型换成游戏内输入，不能假设浏览器输入；前端的重连与代际概念换成进程内会话生命周期，不保留 socket 代际；预览组件的帧消费换成游戏内帧源消费者，不再有网络显示延迟。

这些是 14 的迁移输入，不是 13 的未完成项。这一点必须在交接时反复强调，否则 14 会以为自己在补 13 的欠账。

**迁移顺序**——第一步是 Forge 最小闭环：启动客户端、打开游戏内编辑器界面、用进程内端点挂一个最小脚本、用 GPU 帧源出第一帧、播放暂停 seek、关闭重开。这一步通过之后才做面板迁移，因为如果连一帧都出不来，面板迁移没有意义。

第二步是 Forge 面板迁移：工作台外壳换成游戏内界面，然后按轮次接主轴、双面板、路径、转场、覆盖层、音频调色、行为、模板飞控字幕。每接一个面板先只读与空态，再开放编辑，然后跑对应的黄金脚本。这一步的红线是不允许在 AUI 里另建一套选择、命令或文档模型。

第三步是 Fabric 对等：复用同一套接口、字段目录、文档模型与面板标识，只替换加载器入口与生命周期，不复制 Forge 的业务代码，两条加载器跑同一组黄金脚本。

**交接输入包**——13 交给 14 的东西：01 的接口与命令回执语义；02 的字段目录与 schema 哈希规则；03 的文档模型与序列化、撤销、校验桥；04～12 的面板标识、命令标识与抽屉清单；13-02 的正例负例与期望文件；13-01 的执行记录（明确哪些 P0 与 P1 已通过）；13-07 的发布说明与已知限制；WebUI 与 AUI 的版本显示名规则；迁移顺序。

**交接门禁**——13-01 的 P0 与 P1 全部通过；13-02 的正例负例已执行；13-03 六类工作台场景通过；13-04 Forge 与 Fabric 都通过；13-05 字幕全流程通过；13-06 三项硬化通过；13-07 发布包与安装与首启与连接通过且已知限制已写入发布说明。任一不满足，14 不启动。

**责任边界**——13 对 WebUI 发布负责；14 对 AUI 的宿主、帧源、输入、游戏内呈现负责；01 对接口合同负责；02 与 03 对字段目录与文档模型负责；04～12 对各自面板语义负责。14 发现的任何问题，先判断是宿主迁移问题还是原轮合同问题，后者回原轮修，不在 14 里改语义。

## 四、技术细节

### 4.1 核心模型

交接的本质是把"可替换"与"不可替换"分开。可替换的是承载：谁提供帧、谁接收输入、谁画窗口、谁开连接。不可替换的是语义：一个字段叫什么、一个值怎么序列化、一次修改怎么撤销、一个面板归谁。

14 的验收标准因此可以提前写出来：同一个脚本在 WebUI 与 AUI 上打开、编辑、保存，产物逐字段相同；同一个操作在两边都是一次撤销；同一个面板在两边职责相同。做不到，就是迁移跑偏了。

### 4.2 契约

冻结项：字段目录是唯一字段来源，声明自检与 schema 对账不变，14 不新建第二份字段表也不从快照反推；文档模型的顶层形状、四类集合、未知键策略、值模型、片段身份、无损序列化、撤销、校验桥、打开新建保存推送不变；面板的标识、命令标识、抽屉清单、字段归属、选择模型不变；端点所有权与单端点关闭语义、飞控退出定向、关键回执不静默丢、握手能力与 schema 哈希、总开关关闭后无服务无捕获无按键，全部不变。

可替换项：端点实现、服务端与 token 机制、捕获与编码链路、预览规格假设、窗口与菜单与文件对话框、输入法焦点模型、重连与代际概念、帧消费的显示延迟。

### 4.3 数据形态

能力交接矩阵按"能力 / WebUI 状态 / AUI 目标 / 备注"四列组织。总开关与模式在 AUI 上是同一开关新增游戏内模式，不新开总开关；接口直接复用不复制；字段目录与文档模型直接复用不建第二份；项目图、主轴、双面板在 AUI 换成游戏内呈现但数据与语义相同；路径曲线、转场、覆盖层字幕、音频调色、触发器规则、模板飞控字幕工作流直接复用，其中飞控的输入换成游戏内；预览换成 GPU 帧源不再走网络；输入换成游戏内输入。

### 4.4 边界

14 不允许做的事：重写字段目录；重写文档模型与选择与撤销；新建第二套主时间轴或属性面板或效果面板；把模板变成运行时；把字幕变成第二套 JSON 或 sidecar；把转场做成片段字段；把 `fade` 当 crossfade；把 AUI 做成游戏内嵌 WebView；在 13 里提前实现 AUI。

这些不是风格建议，每一条都对应一类已经被排除过的错误设计，理由写在各轮自己的"为什么不选别的"里。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 让 14 从头设计 | AUI 按游戏内界面重新定义面板与模型 | 可能更贴合游戏内交互 | 同一能力会有两套语义，脚本与撤销行为开始分叉 |
| 整段照搬 WebUI | 把网络端点、预览管线、输入模型搬进游戏进程 | 工作量最小 | 游戏自己连自己、固定规格出帧、浏览器输入模型在游戏里失效 |
| 游戏内嵌 WebView | 把现有前端塞进游戏内浏览器控件 | 几乎零迁移成本 | 拿不到 GPU 帧源与游戏内输入，等于没做 AUI |
| 先做 Fabric 再回填 Forge | 以较简单的加载器开局 | 起步快 | 两条加载器入口差异大，先做简单的会导致后做的一条被迫兼容前者的临时结构 |

**本方案的缺点**：

- 冻结太严会限制 AUI 针对游戏内交互做优化，某些 WebUI 上合理的面板划分在游戏内可能别扭。
- 三步迁移顺序意味着 Forge 走完全程之前 Fabric 完全没有进展，并行度低。
- 责任边界靠人判断"这是宿主问题还是合同问题"，实际执行时容易推诿。

### 6.2 冻结项（14 不得重写）

- 字段目录：唯一字段来源，声明自检与 schema 对账不变；14 不新建第二份字段表，不从快照反推。
