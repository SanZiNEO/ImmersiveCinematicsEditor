# 13-01 验收总账与证据规则

## 目的

把 01～12 的目标合同变成一张可执行、可复验、可追责的验收账。它回答三个问题：

1. 这一轮到底要验什么，不验什么；
2. 每个通过项的证据是什么；
3. 失败后回哪一轮修。

本文件不定义新功能。任何 01～12 没写过的能力，不能借验收之名临时加进来。

## 状态定义

| 状态 | 含义 | 能否发布 |
|---|---|---|
| `PASS` | 按场景执行，证据完整，结果符合合同 | 可以，前提是 blocker 全 PASS |
| `FAIL` | 执行了，结果不符合同 | 不可以 |
| `BLOCKED` | 前置缺失，无法执行；不是通过 | 不可以 |
| `NOT RUN` | 尚未执行 | 不可以 |
| `WARN` | 已执行，存在不影响本次发布的偏差；已记录并有人接受 | 可以作为已知限制发布 |

`BLOCKED` 和 `NOT RUN` 都不能写成“基本通过”。没有证据的“我看了代码，应该没问题”只能算 `NOT RUN`。

## 证据规则

一次验收的证据至少包含：

- 环境：操作系统、编辑器版本、模组版本、Forge/Fabric、游戏版本、ffmpeg 是否可用；
- 输入：黄金脚本路径 + 内容哈希；字幕源文件；资源文件；
- 操作：从启动到结果的可复现步骤；
- 输出：解析/校验结果、脚本 diff、游戏画面截图或录屏、日志片段；
- 判定：`PASS/FAIL/BLOCKED`，失败时写清期望/实际/回退轮次。

禁止作为证据：

- 只截一个菜单，不证明功能执行；
- 只贴源码里有某个字段；
- 只跑 `npm run build` 就宣称游戏通过；
- 用 mock 数据替代真实 `script.validate` / 真实游戏；
- 伪造素材尺寸、最终画面、构建或游戏结果；
- 把旧编辑器的行为当作新合同已实现。

## 发布门禁

13 发布门禁分三级：

| 级别 | 含义 | 处理 |
|---|---|---|
| `P0` | 发布阻断：数据损坏、无法启动、无法连接、无法保存、无法播放、跨端点误操作 | 必须修完并复验 |
| `P1` | 功能阻断：某条目标合同不可用，但有明确回退轮次 | 必须修完或经用户明确降级为已知限制 |
| `P2` | 体验偏差：不影响正确性，文案/布局/提示问题 | 可记录为已知限制，不阻断发布 |

P0/P1 不允许“先发布再修”。P2 必须有明确接受人和发布说明条目。

## 环境矩阵

| 环境 | 用途 | 是否发布门禁 |
|---|---|---|
| Windows + Electron 真窗口 | 工作台、文件、窗口、IME、发布包 | 是 |
| Windows + Forge + 真游戏 | WebUI→Forge 全链路 | 是 |
| Windows + Fabric + 真游戏 | WebUI→Fabric 全链路 | 是 |
| 无 ffmpeg 的 Forge/Fabric 环境 | H.264 回退 RGBA、外部音频失败提示 | 是，至少一条加载器 |
| 断网/断连/游戏退出 | 错误、重连、关闭 | 是 |
| 无 AUI 环境 | 确认 13 不依赖 AUI | 是 |

如果 Fabric 环境当前不可用，13 状态是 `BLOCKED`，不是“Fabric 逻辑上应该可以”。
