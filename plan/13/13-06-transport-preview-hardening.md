# 预览、传输与关闭硬化

> 状态：未实现
> 范围：预览规格与界面一致、资源扩展名与运行时能力对齐、关闭幂等三项硬化，以及传输、帧消费、预览流的既有合同验收
> 关联：13-01 总账、13-04 真游戏冒烟、13-07 发布基线、01 与 03 的端点与传输合同

## 一、摘要

这一份同时做两件事：收掉三项具体的不一致，以及把传输、预览、帧消费、teardown 的既有合同验一遍。三项硬化是预览规格在界面上与服务端固定值一致、资源列举的视频扩展名与运行时实际能力对齐、预览屏关闭的幂等。其余部分不新增协议、不新增消息名、不改帧头、不新增第二套预览管线——只按现有合同验，失败回原轮。

## 二、为什么做

### 2.1 问题

三处不一致各自都会让作者困惑。预览规格上，服务端早已固定成 1920×1080@60 并忽略请求里的档位，前端却还摆着 original、720p、1080p 与 30/60fps 的选择器；作者选了什么都不会生效，状态栏显示的和实际捕获的还可能不是一回事。资源列举上，视频扩展名与运行时能力对不齐，会出现"能播放但列举不到"或"列举了却打不开"，作者分不清是文件坏了还是编辑器不认识。关闭上，预览屏的关闭入口没有守卫，重复关闭可能再次触发播放退出、重复停止服务，甚至在另一个窗口仍连着的时候把服务停掉。

传输层的风险不是"能连上就行"：帧头、时间戳、帧消费队列、VideoFrame 释放这些地方一旦错，症状是偶发黑屏、长时间预览内存增长、seek 后停在旧帧，很难在事后定位。

### 2.2 目标

- 界面不再提供预览档位选择，状态栏只读显示固定规格，回执异常时显示异常而不是静默改档位。
- 资源列举按类型返回运行时真正支持的扩展名，无 ffmpeg 时外部音频的状态明确。
- 关闭幂等：第一次关闭做清理，后续关闭直接返回；单端点关闭只释放本会话。
- 传输与帧消费的关键行为按现有合同逐项成立，没有静默丢回执。
- 不新增协议、消息名、帧头或第二套预览管线。

### 2.3 非目标

- 不改帧头的顺序、宽度与类型，不改 RGBA 与 H.264 的解析契约。
- 不改握手、token、Origin、代际与超时的语义。
- 不改飞控 owner 与退出定向，不改规则、模板、字幕、转场的语义。
- 不为迎合旧文档去给运行时加它本来没有的格式支持。

以上都属于"只验收、失败回原轮"，13 不借硬化之名重写传输层。

## 三、方案

**预览规格统一**——服务端已经固定：预览配置忽略请求字段，回执固定模式、宽高、帧率、关键帧与编码器开关，线上名固定。前端要收掉旧档位：删除 original、720p、30fps 的选择器；状态栏只读显示固定规格；不再让用户"选择预览档位"；`editor.previewConfig` 只作为查询与回执，不再表达用户选择；回执宽高帧率与固定值不一致时，状态栏显示异常而不是悄悄换档。状态栏可以显示固定规格、实际捕获宽高、编码器是 H.264 还是 RGBA、首帧状态与丢帧计数。

验收上看的是：打开编辑器，预览设置页与状态栏没有档位选择器；连接前后都显示固定规格；切换窗口或重连后不会回到 original；服务端回执是固定模式，前端不显示旧档位名；删掉选择器之后仍然持续请求帧；实际尺寸异常时可见，不假装是 1080p。

**资源扩展名对齐**——列举必须与运行时实际能力一致。当前实际支持：图片是 png 与 gif；视频是 mp4、webm、mkv；OVERLAY 的 `image.path` 接受 png、gif、mp4、webm、mkv；音频是 ogg 与 wav，有 ffmpeg 时再增加 mp3、aac、flac、m4a、opus、wma、oga、ogx。jpg、jpeg、webp、mov 当前运行时没有对应支持，不作为必过项，也不把旧提案当成已实现能力。

行为上：按图片类型列举只返回 png 与 gif；按视频类型列举返回 mp4、webm、mkv；按全部列举返回全部文件；按音频列举返回 ogg 与 wav，ffmpeg 可用时增加外部白名单，不可用时明确只支持这两种。资源路径仍是资源根下的相对路径，越界拒绝，超限返回截断标记并由前端显示"还有更多"；抽屉按类型分栏，不把视频塞进图片栏；选中视频后能保存并能播放；没有 ffmpeg 时"可列举但不可播放"的状态要明确，不伪造成功。

**关闭幂等**——预览屏的关闭入口需要守卫，并且与移除回调共用同一段 teardown。第一次关闭执行清理，后续关闭直接返回。清理顺序固定：飞控取消（仅当本端点拥有）、编辑器播放退出、本端点预览流关闭、服务端停止（仅宿主级 teardown）、键位冷却。

单端点关闭只释放本会话：不停服务端（除非这是宿主级关闭），不关捕获中心，不取消其他端点的飞控，不关其他窗口的预览流。世界退出走宿主级 teardown，清理预览屏、服务与预览流，无残留端口、捕获消费者、按键与 token。总开关关闭才做宿主级 teardown——关闭幂等不等于"任何关闭都停服务"。

验收上按顺序做：开两个编辑器窗口，关窗口 A 看窗口 B 是否继续出帧；关窗口 B 看服务是否按宿主规则停止；对同一个屏重复调关闭；世界退出再重进；总开关关闭再开启；在关闭一个窗口时让另一个窗口正在飞控。必须成立的是：A 关闭后 B 仍连接仍出帧；捕获中心未被关闭；他人飞控未被取消；重复关闭无异常且不误停游戏播放；世界退出无残留；总开关关闭后两种模式都进不去，重复关闭也无异常。

**传输与会话验收**——按现有合同逐项验，不改语义。

握手：本地回环地址与固定路径；token 为十六进制串；Origin 白名单；无 token 不发起无意义连接；token 轮换后重连能重新读取；多客户端不选举也不互相踢；单会话关闭只释放本会话。

消息：信封形状不变；握手回执带版本、能力与 schema 哈希；回执能区分成功与失败；`flight.exit` 只到 owner 不广播；没有 id 的错误要在状态栏可见；关键回执（保存、飞控退出、命令回执）不可静默丢；状态类文本可合并，关键文本绝不静默丢。

预览线格式：帧头为固定字节序与长度；两种帧类型（RGBA 与 H.264）与关键帧标志不变；RGBA 载荷长度不小于宽乘高乘四，多余字节忽略；帧序号只作诊断与配对，不参与播放时间；时间戳会话内单调且不溢出；编码器字符串固定；不改头顺序、宽度与类型。

帧消费：显示延迟固定；队列有上限；时间戳回退与断流要能重同步；H.264 等关键帧再解码；RGBA 走图像数据直写；VideoFrame 每条路径都释放；首帧超时要提示；帧监听支持多监听（若仍是单回调，属回原轮项）；漂移修正只在一处生效，不双重修正。

预览流：服务端固定规格；暂停由播放状态驱动而不是由渲染回调驱动；暂停补帧有预算；统计区分"已捕获"与"首帧"；关闭只注销本消费者与本会话，不关捕获中心；编码器关闭器异步回收，不阻塞渲染线程。

## 四、技术细节

### 4.1 核心模型

三项硬化的共同点是"消除两套真相"：预览规格只能有服务端一个来源，前端是只读视图；资源扩展名只能来自运行时能力，列举与打开共用同一份；关闭只有一个入口语义，第一次与后续调用行为一致。

传输验收的核心模型是"关键路径不可静默"：握手、保存回执、飞控退出这三类文本一旦丢失，编辑器就会处于自己也不知道的状态。状态类文本可以合并以省带宽，关键文本必须逐条到达。

### 4.2 契约

允许直接改的只有三处：预览档位的界面枚举、默认值与请求体；资源列举的类型与扩展名与截断；预览屏关闭的守卫与共用 teardown。服务端已经固定的规格不回退成可配档位。

其余全部只验收不改：帧头、帧类型与标志；RGBA 与 H.264 解析契约；握手、token、Origin、代际、超时；帧消费队列、时间戳与 VideoFrame；飞控 owner 与退出定向；规则、模板、字幕、转场语义。

### 4.3 数据形态

保留的证据：预览设置页与状态栏截图（证明没有档位选择器）；资源按四种类型请求的响应；关闭幂等的录屏与日志（双窗口、重复关闭、世界退出）；预览首帧、暂停、seek 与统计截图；断连重连的抓包或日志；协议头与时间戳日志（不泄露 token）。

### 4.4 边界

13-06 不改业务语义。任何在验收中发现的字段、面板、模板、字幕、转场、飞控问题都回 01～12 对应轮，不在这一份里"顺手修"。硬化的三处改动完成后要回到 13-04 复验关键路径。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 保留档位选择器 | 前端仍可切 original/720p/1080p，服务端忽略 | 界面不改 | 作者选了不生效，属于欺骗性界面 |
| 让服务端支持多档位 | 把固定规格改成可配 | 界面与后端一致 | 引入新的运行时分支与测试面，13 是发布轮不是功能轮 |
| 关闭不幂等，靠调用方自律 | 约定只调一次关闭 | 改动最小 | 重复关闭来自真实路径（重复按键、世界退出叠加），约定管不住 |
| 顺手重写传输层 | 借硬化把帧头与消费一起重做 | 一次做干净 | 会把发布轮变成风险最高的重写轮，且失败后无法归因 |

**本方案的缺点**：

- 删掉档位选择器后，作者失去了降分辨率的省算力选项，弱机器上没有退路。
- 资源扩展名只对齐现有能力，作者拿到 jpg 或 mov 时仍然不能用，只能自己转换。
- 关闭顺序是硬编码的，未来新增端点类型时要重新审一遍顺序。
