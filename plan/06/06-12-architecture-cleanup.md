# 架构整理：把职责从按轮次堆改成按层分

> 状态：未实现
> 范围：`src/` 的目录分层与职责边界、胖控制器拆分方向、跨轮概念的落点、共享交互的归属
> 关联：06-01 至 06-11 的落点约束，07～12 的实现位置

## 一、摘要

前五轮把地基立起来了：`core/` 是纯逻辑，`workbench/` 是骨架，`plugins/` 是面板插件，分层本身干净。问题在层内——切分跟着轮次走，没有跟着职责走。本文定义一次结构收口：把跨面板的业务内核收进 `features/`，让 `plugins/` 只剩装配，并把胖控制器按变化理由拆开。它不阻塞 06 的功能实现，但约束 07～12 把新东西放在哪里。

## 二、为什么做

### 2.1 问题

现在改的成本是"移动文件 + 拆职责"；等 11、12 都写完之后再改，成本是"移动文件 + 重写调用链 + 重跑全部验收"。所以放在 06 末尾做，是最后一次便宜的机会。

具体有四个症状。控制器成了什么都知道的对象：图控制器同时管加载、布局调度、动画帧推进、悬停计时、手势暂停、对话框开合与手摆坐标写盘，任何一处要改都得读这个文件；时间轴控制器与时间轴面板有同样的问题。轮次概念漏进了面板壳：属性面板目录里住着 11 轮的行为字段面，06 还没写完，11 的东西已经搬进去了，等 11 真正要做时面临"搬走还是复制"的两难。跨轮基础设施没有落点：组合编辑、面板归属策略、交界模型都是被多轮共用的东西，但只在文档里点了名，`src/` 里没有对应位置，于是每轮实现时各写一份。共享交互没有归属：悬停卡片、弹出对话框、拖动手势、键盘导航在 05 已各写一遍，06～12 每个面板都会再需要，现在散在某个插件内部，别的插件要用只能复制。

### 2.2 目标

- 新增一个面板时，业务逻辑有明确落点，插件目录只放装配代码。
- 任一控制器文件只承担一类状态；读它能回答"它为什么会被改"。
- 跨轮共用的概念（归属策略、组合编辑、交界模型）各只有一份实现。
- 共享交互模式（悬停、弹出、手势、键盘）各只有一份实现。
- 迁移不改变对外行为：全部自检与两套 e2e 保持通过。

### 2.3 非目标

- 不重写已有功能，不改变交互。
- 不引入新框架、不改构建配置、不改依赖。
- 不为"以后可能用到"预建空目录：目录随实现长出。
- 不追求文件行数指标；判断标准是变化理由的数量。

## 三、方案

目标结构是按层分，不新增按轮次的目录。`core/` 保持纯逻辑不动；新增 `features/` 承接跨面板的业务内核，按领域再分（效果与面板归属、组合编辑与路径生成、行为与条件树、交界与叠化、模板与字幕编译、资源与媒体检查）；`workbench/` 保持骨架不动，另设共享交互区；`plugins/` 变薄，每个插件只保留 manifest、面板组件，以及把 feature 接到面板上下文的胶水。

两条关键变化。第一，`features/` 可以被多个插件引用，但不引用任何插件、不引用 Vue 组件，只依赖 `core` 与工作台 API——它是纯函数与轻量状态机的集合。第二，`plugins/` 只做装配，插件之间仍然不互相引用，共享一律走 `features` 或服务注册的令牌。

迁移分四个方向，不列具体清单。

拆分胖控制器：图与时间轴的控制器按职责拆开，一个文件只留一类状态——数据加载与失效、视图与布局调度、交互状态（悬停、选中、手势）、对话框与编辑目标、持久化。拆法不追求每个文件多少行，而是让一个文件只有一个变化理由。拆分后原控制器变成组合者，对外接口不变。

把跨轮概念搬出面板壳：触发器、规则、条件树的字段面从属性面板迁到行为领域；属性面板只保留属性行、值控件与时钟。面板归属策略从组件里抽出来，进效果领域。

给跨轮基础设施立位置：组合编辑、路径生成、预览采样按 07 的点名放进授权编辑领域；交界与叠化模型按 08 的点名放进过渡领域。不是先建空目录，而是每轮实现时直接落到对应位置，不再往插件目录里塞。

抽出共享交互：悬停、弹出、手势、键盘导航抽成工作台的共享交互区，供所有面板复用。这是唯一"现在就值得做"的一项，因为 06～12 每个面板都会重写一遍，不抽出来会线性膨胀。

边界约束必须守住，否则等于把结构问题换个地方：`core/` 仍然零 DOM、零 Vue、零 Electron；`features/` 不引用插件、不引用 Vue 组件，可以有纯函数与轻量状态机；`plugins/` 之间仍然零引用，共享走 `features` 或服务注册令牌；`workbench/` 不引用 `features/` 的具体实现，只经 API 端口；迁移期间不改变对外行为，全部自检与两套 e2e 保持全绿。

## 四、技术细节

### 4.1 核心模型

四层，各自只有一个职责方向：`core/` 是纯逻辑（文档、图、schema、时间轴），零 DOM 零 Electron；`features/` 是跨面板业务内核，可被多插件引用、只依赖 core 与工作台 API；`workbench/` 是骨架（端口、服务、宿主、布局、命令、共享交互）；`plugins/` 是装配（manifest、面板组件、接线）。

判断某个文件该放哪一层的依据是它的依赖方向，而不是它的来源轮次。凡是需要被两个以上插件使用、又不涉及具体渲染的，属于 `features/`。

### 4.2 契约

- 依赖只能向内：`plugins/` 依赖 `features/` 与 `workbench/`，`features/` 依赖 `core/` 与工作台 API，`core/` 不依赖任何上层。
- `plugins/` 之间零引用；需要协作时通过 `features/` 或服务注册令牌。
- `workbench/` 不引用 `features/` 的具体实现，只经 API 端口。
- 迁移不改变对外行为：接口签名、交互流程、数据形态都不变。

### 4.3 数据形态

没有新的持久化数据。迁移只改变代码位置与模块边界，文档形态、会话形态、序列化结果都不变。目录本身也不是数据：空目录不预建，随实现长出。

### 4.4 边界

- `core/` 不引入 DOM、Vue、Electron。
- `features/` 不引用插件，也不引用 Vue 组件。
- `plugins/` 之间不互相引用。
- 迁移期间不改交互、不改数据形态、不改构建配置。

## 五、为什么不选别的

| 备选方案 | 做法 | 代价 | 为什么没选 |
|---|---|---|---|
| 继续按轮次堆 | 每轮新增的东西就近塞进现有插件 | 短期最省事；到 12 轮时插件目录成为第二个单体 | 越晚改成本越高，06 末尾是最后一次便宜的机会 |
| 一次性大重写 | 按目标结构重写全部控制器 | 风险高，回归面覆盖全部验收 | 只移动与拆分，不改行为，风险可控 |
| 只拆控制器不建 features | 保持四层现状，只把胖文件拆小 | 跨轮共用概念仍无落点，各轮继续各写一份 | 拆文件解决不了归属问题 |
| 先建空目录占位 | 按目标结构把目录一次性铺开 | 空目录无实现，读代码时误导 | 目录随实现长出，不预建 |

**本方案的缺点**：

- 迁移期两套位置并存，读代码需要确认哪个是活的。
- `features/` 与 `plugins/` 的边界需要持续判断，判断错就退化成"又一个杂物间"。
- 拆分控制器会让调用链变长，单步调试需要多跳几层。
